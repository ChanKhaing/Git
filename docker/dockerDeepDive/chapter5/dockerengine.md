


📘 အခန်း (၅) - The Docker Engine (Docker အင်ဂျင်ရဲ့ အတွင်းပိုင်း)

၁။ Concept (အဓိက သဘောတရား) - "Docker Engine ဆိုတာ ဘာလဲ၊ ဘယ်လိုအလုပ်လုပ်လဲ"

Docker Engine က ကွန်တိန်နာတွေကို မောင်းနှင်တဲ့ အဓိက Software (Core) ပါ။ ဒါကို နားလည်ဖို့ စားသောက်ဆိုင် (Restaurant) ဥပမာ ကို ကြည့်ပါ။

ခင်ဗျား စားသောက်ဆိုင်တစ်ဆိုင်မှာ ညစာ (Container) မှာတယ်ဆိုပါစို့။

၁။ Docker Client (docker command) = ဒါက ဧည့်ကြိုလူကြီး (Waiter) ပါ။ ခင်ဗျားက "ညစာတစ်ခွက် ပေးပါ" (docker run) လို့ မှာလိုက်တယ်။

၂။ Docker Daemon (dockerd) = ဒါက မီးဖိုချောင်မှူး (Head Chef) ပါ။ ဧည့်ကြိုရဲ့ အမိန့်ကို လက်ခံပြီး "ညစာ ချက်ပြုတ်ဖို့" အောက်ခြေလူတွေကို ညွှန်ကြားတယ်။ ဒါပေမယ့် မီးဖိုချောင်မှူးက ကိုယ်တိုင် ချက်လေ့မရှိဘူး။

၃။ containerd = ဒါက မီးဖိုချောင်မှ လက်ထောက်မှူး (Sous-Chef) ပါ။ သူက မီးဖိုချောင်မှူးဆီက အမိန့်ကို လက်ခံပြီး "ဒယ်အိုးပေါ် ထည့်ချက်ဖို့" အောက်ခြေ ထမင်းချက်ကို ခေါ်တယ်။ ကွန်တိန်နာတွေရဲ့ ဘဝစက်ဝန်း (Lifecycle) - စတာလား၊ ရပ်လား၊ ခဏရပ်လား (pause) ဆိုတာကို ဒီအဆင့်မှာ စီမံတယ်။

၄။ runc = ဒါက တကယ့် ထမင်းချက် (Line Cook) ပါ။ ဒီအဆင့်မှာမှ ကွန်တိန်နာ (ညစာ) ကို တကယ် ဖန်တီးတယ်။ ဒါပေမယ့် သူက ကွန်တိန်နာ စတာနဲ့ ပြီးရင် သူ့အလုပ် ပြီးသွားတယ် (runc process က ထွက်သွားတယ်)။

၅။ shim = ဒါက ထမင်းချက်ရဲ့ အကူ (Kitchen Helper) ပါ။ runc ထွက်သွားပြီးတဲ့အခါ ကွန်တိန်နာကို ဆက်ပြီး စောင့်ကြည့်ပေးတယ်။ ဥပမာ - ကွန်တိန်နာက ဘာထွက်လဲ (logs) ကို ဆက်ပြီး မီးဖိုချောင်မှူး (Daemon) ကို ပြန်ပို့ပေးတယ်။ အထူးသဖြင့် Daemon ကို Restart ချလိုက်ရင်တောင် ကွန်တိန်နာတွေ ဆက်ပြီး အလုပ်လုပ်နေအောင် ဒီ shim က လုပ်ပေးတယ်။ (စာအုပ်ထဲမှာ "Daemonless containers" လို့ ခေါ်တယ်)။

---

၂။ Hands-on / Step-by-Step (လက်တွေ့ လိုက်လုပ်ရမည့် အဆင့်များ)

ဒီအဆင့်တွေက ခင်ဗျားရဲ့ စက်ထဲမှာ ဒီအစိတ်အပိုင်းတွေ အလုပ်လုပ်နေတာကို မျက်စိနဲ့မြင်အောင် လုပ်ပေးမှာပါ။

အဆင့် ၁: Docker Daemon (dockerd) ကို ရှာဖွေခြင်း

# Command: ps aux | grep dockerd
# ps aux က လက်ရှိ ပြေးနေတဲ့ လုပ်ငန်းစဉ် (Process) အားလုံးကို ပြတယ်။
# grep dockerd က dockerd ဆိုတဲ့ စာလုံးပါတဲ့ လုပ်ငန်းစဉ်ကိုပဲ ထုတ်ပြတယ်။
# ဒါက ခင်ဗျားရဲ့ Docker Daemon (Head Chef) ရဲ့ Process ID (PID) ကို ပြပေးမယ်။
ps aux | grep dockerd
မှတ်ချက် (Comment): စာအုပ်ဟောင်းမှာ dockerd ကို ဖော်ပြထားပေမယ့် အခုအခါမှာ ဒါကို /usr/bin/dockerd အနေနဲ့ တွေ့ရမှာပါ။ ဒါက ပုံမှန်အတိုင်းပါ။

အဆင့် ၂: containerd ကို ရှာဖွေခြင်း (Sous-Chef)

# Command: ps aux | grep containerd
# containerd က Docker Daemon အောက်မှာ ကွန်တိန်နာတွေရဲ့ အသက်ကို စီမံတဲ့ အဓိက Runtime ပါ။
ps aux | grep containerd
မှတ်ချက် (Comment): စာအုပ်ထဲမှာ docker-containerd လို့ ခေါ်ထားပေမယ့် အခုအခါမှာ ဒါက containerd ဆိုပြီး သီးခြား Project တစ်ခုဖြစ်သွားပြီး (CNCF အောက်မှာ)၊ ဒီအတိုင်း သီးခြားရှိနေပါပြီ။

အဆင့် ၃: runc ကို ရှာဖွေခြင်း (တကယ့် ကွန်တိန်နာ ဖန်တီးသူ)

ဒါကို မြင်ဖို့ ကွန်တိန်နာတစ်လုံး ပြေးနေမှ ပေါ်မှာပါ။ ဒါကြောင့် ကွန်တိန်နာအသစ် စတင်ပြီး စစ်ကြည့်ပါ။

# Container အသစ် စတင်ခြင်း (နောက်ခံမှာ အမြဲပြေးနေအောင်)
docker container run -d --name test-runc alpine sleep 1d

# runc process ကို ရှာဖွေခြင်း
# sleep 1d ကို runc က ဖန်တီးလိုက်တဲ့ ကွန်တိန်နာထဲမှာ ပြေးနေတာကို တွေ့ရမယ်။
ps aux | grep runc

# ပြီးရင် သန့်ရှင်းအောင် ဖျက်ပါ။
docker container rm -f test-runc
အဆင့် ၄: shim process ကို ရှာဖွေခြင်း (Helper)

# ကွန်တိန်နာတစ်လုံး ပြန်စတင်ပါ။
docker container run -d --name test-shim alpine sleep 1d

# shim process ကို ရှာဖွေခြင်း
ps aux | grep containerd-shim
မှတ်ချက် (Comment): ဒီ shim က runc ထွက်သွားပြီးတဲ့အခါ ကွန်တိန်နာကို ဆက်ပြီး စောင့်ကြည့်ပေးတယ်။ ဒါကြောင့် ခင်ဗျား Docker Daemon ကို sudo systemctl restart docker လို့ ရပ်လိုက်တောင်မှ ဒီ shim ရှိနေသေးလို့ ကွန်တိန်နာတွေ ဆက်ပြီး အလုပ်လုပ်နေမှာပါ။ (စာအုပ်ထဲက "daemonless containers" ဆိုတာ ဒါပါ)။

# သန့်ရှင်းအောင် ဖျက်ပါ။
docker container rm -f test-shim

### ### #### #### ##### #### #### #### #####
၃။ Key Takeaways & Best Practices (သတိထားရန်နှင့် မရှိမဖြစ် မှတ်သားရမည့် အချက်များ)

ဒီအခန်းပြီးသွားရင် အောက်ပါ အချက် (၃) ချက်ကို သေချာမှတ်ထားပါ။

၁။ Docker Daemon က ကွန်တိန်နာကို ကိုယ်တိုင် မဖန်တီးတော့ဘူး

· ရှေးခေတ်တုန်းက Daemon က ကိုယ်တိုင် လုပ်ခဲ့ပေမယ့် အခုအခါမှာ Daemon က containerd ကို ခေါ်တယ်၊ containerd က runc ကို ခေါ်တယ်။ ဒါက Modular Design (အစိတ်အပိုင်းခွဲထားတဲ့ ဒီဇိုင်း) ဖြစ်လို ပြုပြင်ထိန်းသိမ်းရ လွယ်ကူတယ်။

၂။ OCI (Open Container Initiative) စံချိန်စံညွှန်းကို လိုက်နာတယ်

· Docker က runc (OCI Runtime Spec) ကို သုံးတယ်။ ဒါကြောင့် တခြား OCI-compliant tools တွေနဲ့ အလွယ်တကူ အစားထိုးလိုရတယ်။ (ဥပမာ - Kubernetes က containerd ကို အစားထိုးသုံးနေတယ်)။

၃။ Daemon Restart လုပ်ရင် Container မသေဘူး (Daemonless Containers)

· shim process က ကွန်တိန်နာကို Daemon နဲ့ သီးခြားခွဲထားတယ်။ ဒါကြောင့် Docker Daemon ကို Upgrade လုပ်ဖို Restart ချလိုက်ရင်တောင် ခင်ဗျားရဲ့ ကွန်တိန်နာတွေ ဆက်ပြီး အလုပ်လုပ်နေမှာပါ။ (Production အတွက် အရမ်းအရေးကြီးတဲ့ အချက်ပါ)။

---

⚠️ သတိထားရမည့် အချက် (Warning)

စာအုပ်ထဲမှာ docker-containerd နဲ့ docker-runc လို ခေါ်ထားပေမယ့် အခုအခါမှာ ဒါတွေကို containerd နဲ့ runc လိုပဲ ခေါ်ပါတယ်။ (မျဉ်းစပ် docker- ဆိုတဲ့ အပိုင်း ပျောက်သွားပြီ)။ ဒါပေမယ့် သူတိုရဲ့ အလုပ်လုပ်ပုံက အတူတူပါပဲ။
